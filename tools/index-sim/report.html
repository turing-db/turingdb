Indexing a versioned graph, five ways

Each design keeps a string-property index across an immutable, git-like commit history. As parts accumulate 1 → 2,000, read and submit latency pull apart sharply — the designs with the cheapest writes pay the most expensive reads, because every commit's parts must be collected and merged at read time. No structure wins on every axis; the verdict at the end routes the choice by workload.

the requested design, in detail

Per-DataPart index: the cost of collecting at read time

Each immutable part carries a local index built once over its own write-set. A read fans out across all parts and merges the hits — O(parts), unconditionally. A per-part Bloom/zone-map filter lowers the constant; compaction (bounding live parts to K) changes the slope.

collect all parts collect + per-part prune compacted to K=64 parts multiversion (reference)

A per-DataPart index is exactly what TuringDB builds for edges and string properties, and the model ClickHouse uses. Pruning the misses (Bloom/zone-map) lowers the constant — ~60 µs vs ~170 µs at 2,000 parts — but the slope stays O(parts). Compaction is what flattens it: bounding live parts to K=64 holds reads at ~5.5 µs however long history grows. It isn't free — merging rewrites each entry repeatedly, so submit climbs from 2.1 µs to ~12.8 µs (write amplification). That read-for-write trade is why ClickHouse leans on aggressive background merges — and why a version-preserving store, which can't simply discard old parts, still leans toward the global multiversion structure (flat 165 ns, no merging).

A single mutex serializes — latency grows linearly with writers (166 µs at 64). Striping by 256 nearly erases contention. Lock-free CAS stays flat at 2.6 µs — until a hot key (--hot) turns every write into a retry storm.

Reading under writers, and reading into the past

The earlier panels read at HEAD, single-threaded. Two things change that — concurrent writers, and time-travel (as-of) reads — and each ranks the designs completely differently.

Reader latency vs concurrent writers — every design

HAMT COW B-tree COW layers Per-DataPart MV lock-free MV global mutex

Every copy-on-write and persistent design publishes a new version with a single atomic root/manifest swap, so reads are wait-free — flat against any number of writers, each at its own base cost. Only the multiversion table mutates shared state on write: lock-free keeps its reads flat (165 ns), but a global mutex drags them to 164 µs at 64 writers — as slow as the per-part fan-out. Reader/writer contention is a property of in-place mutation, not of versioning.

As-of read — latency vs commits behind HEAD (time-travel)

HAMT COW B-tree Multiversion COW layers Per-DataPart

Time-travel reverses the ranking. Persistent trees jump straight to a retained root, so any version reads in ~O(log N) — flat (a touch cheaper deep in history, when the tree was smaller). Per-part and layer reads get cheaper the further back you look: only the parts live at that snapshot are touched. But the multiversion table gets worse — resolving an old snapshot means filtering past every newer version, climbing from 165 ns at HEAD to ~164 µs 2,000 commits back (shown for a key updated each commit; a stable key stays flat). The design that wins the present loses the past.

Structural sharing is the whole game: a naive full copy per commit would cost ~2.1 GiB; every sharing design stays in the low tens of MiB. The per-DataPart and COW-layer storage is the leanest (they store only each commit's write-set); the B-tree's wide nodes make it the heaviest.

global conclusions

No single winner — indexing is a routing decision

Across read latency, write latency, read and write concurrency, and memory, no design dominates. The choice turns on two properties of each indexed column: how its reads arrive — HEAD vs historical, point vs range — and how it churns — cardinality × update rate.

DesignStrongest atFalls over whenReach for it when
Multiversion hash O(1) HEAD reads; smallest memory historical / as-of reads (version filtering), hot keys, coarse write locks low-cardinality, stable, HEAD-read properties — with lock-free or striped writes
COW B-tree balanced read + write; free range scans on dict codes per-write allocation; heaviest memory ordered or range queries
HAMT balanced; flat in history; as-of as cheap as HEAD per-write allocation cost the safe default when the workload is unknown
Per-DataPart, compacted cheapest writes; tiny memory; cheap historical reads reads O(parts) without compaction; compaction adds write amplification write-heavy, scan-tolerant columns — TuringDB's existing per-part model
COW layers cheapest writes reads walk the whole stack, O(parts) append-mostly data, paired with Bloom filters
Global structures buy flat reads. One shared index reads in O(1)/O(log) regardless of history — but the only mutable global one, the multiversion hash, pays for it in write contention unless it goes lock-free.
Local structures buy cheap writes. Per-part indexes let every commit write independently with minimal memory — but a read fans out across all parts, O(parts).
Compaction is the only slope-killer. It bounds read fan-out to O(K), but trades it for write amplification — and a version-preserving store can't discard old parts the way ClickHouse does, so it buys less here.
Time-travel inverts the ranking. Read into the past and the order flips: persistent trees stay flat (any version is a retained root), per-part/layer reads get cheaper (fewer parts existed then), the multiversion table gets costlier (more versions to filter). What wins HEAD loses history.
Wait-free reads come from copy-on-write, not versioning. Every design that publishes a version with one atomic swap gives readers wait-free access; only the in-place-mutable multiversion table must go lock-free to avoid reader/writer contention.

For TuringDB: one structure shouldn't index every property — route by cardinality × churn

  • Low-cardinality, stable string properties (status, type, label — the "identical mostly everywhere" case) → a multiversion structure keyed by dictionary code, lock-free or striped. Flat 165 ns HEAD reads and ~MiB memory from shared, rarely-rewritten posting lists; version filtering bites only on the rare as-of read.
  • High-cardinality or high-churn properties → per-DataPart local indexes (what TuringDB already builds) plus version-preserving compaction to bound fan-out and zone-map / Bloom pruning to cut the constant.
  • Range or ordered access → a COW B-tree per commit; dictionary codes are ints, so range scans come free.
  • Unknown or mixed workload → the persistent trees (HAMT / COW B-tree) are the conservative default — logarithmic and flat on both reads and writes, with history free to query.

Compaction is the universal lever, but it must be version-preserving — which is exactly why the global multiversion structure stays attractive for the stable, low-cardinality slice, and why per-part fan-out is a harder problem here than in a store that can merge history away.

How this is computed

index_sim executes the read/write workload so operation counts — tree depth, layers walked, parts collected, version-chain length — reflect the real access distribution. It then charges each operation a fixed estimated cost: a cache-miss pointer chase (80 ns), a node allocation (60 ns), a CAS (20 ns), a mutex lock (25 ns), a Bloom probe (30 ns). Concurrency wait time is derived from those constants and a writer count — no threads are spawned.

Retune any constant and rerun: ./index_sim --hop 120 --threads 16 --hot 0.05. The shapes are the message; the absolute nanoseconds are only as good as the constants you feed it.
