Improving the HAMT for strings

The prior study found the lock-free multiversion hash wins HEAD reads and the HAMT wins time-travel. This one asks: for string keys, how far can the HAMT's read / submit / memory gap be closed — without surrendering the structural wins that make a persistent structure the right fit for a git-like commit model? The answer is to stop hashing.

The premise

What “for strings” changes

The earlier model charged a flat hash = 5 ns and compare = 2 ns. For real string keys both are O(length) — and where the bytes live drives both memory and the concurrency story.

  • A hash trie hashes the key once per lookup; the multiversion hash hashes on every slot probe, and a dictionary hashes again to assign a code.
  • A radix trie hashes nothing — it descends by the key's bytes, so the structure is the comparison. That is the structural reason ART pulls ahead as keys grow.
  • Interning to dense codes makes compares cheap and dedups bytes — but assigning a code to a new string needs a concurrent dictionary, a write-side bottleneck that hits the lock-free hash hardest.

With a cache-miss hop at 80 ns, per-byte string costs only rival a hop for long keys — so for short keys tree depth dominates, and for long keys the hashing itself becomes first-order. ART avoids the latter entirely.

Four tunings

Improving the hash trie itself

Three of these shrink the gap; the fourth is a correction — dictionary coding is not the read win it's assumed to be.

01 — submit / memory

Fold the commit

Apply the whole write-set to one edit-tagged private copy (Clojure transients), then freeze with a single root publish. A node shared by several writes is copied once, not per write.

−34% submit at 32 writes/commit, −59% at bulk; cuts memory the same way. Literature: 1.5–4× faster bulk builds.
02 — read ⇄ write

Widen the fan-out

Depth drives read hops; width drives copy volume on write. Branch 32 sits below the read-optimal for 100k keys — 64-way dominates it on both axes (depth 4→3).

342 ns read, 11.9 µs submit at branch 64. Reaching hash read-parity needs branch ≈ 512, where submit balloons.
03 — memory

Compact the nodes (CHAMP)

Two bitmaps split data from sub-nodes into one dense, hole-free array. Same hop count, smaller nodes — and sub-linear structural equality, which makes diffing two commits' indexes cheap.

−38% memory in the model (paper reports up to −64% on the JVM). Ships in Scala 2.13.
04 — a correction

Dictionary-code the keys

Tempting to read as a speed win. It is not: coding adds an ~80 ns intern hop, and a HAMT does only one compare per lookup — so it trades a 9 ns string compare for that hop.

A net loss on point reads. Code for memory, ordering, and B-tree/collision compares — not for the trie lookup.
The fan-out frontier

Depth buys reads; width costs writes

Each point is a branching factor. Moving right-to-left, wider nodes shrink the tree and cut read latency — but past the knee at 64, copying ever-wider nodes drives submit back up. There is a real Pareto frontier, and the default 32 is not on it.

The decisive move

For strings, a persistent radix tree (ART)

ART (Leis et al., ICDE 2013) is a byte-wise radix tree with adaptive nodes (Node4/16/48/256), path compression, and lazy expansion. For string keys it is structurally better than a hash trie: it hashes nothing, is shallower (256-way → depth 2–3), is ordered (free range and prefix scans — exactly what TuringDB's StringIndex already wants), and shares prefixes for the smallest memory here. Version-retention copy-on-write ARTs already ship — PART (UC Berkeley), VART (SurrealDB), PermART (SIGMOD 2026).

ART's weakest axis is submit (11 µs at 100k keys — dense upper nodes promote to Node256 and cost like a wide HAMT node), still 2–3× the hash. But at bulk loads even that inverts: at 1,000 writes/commit ART's folded submit (99 µs) beats the hash (140 µs).

Inherent, not tunable

The four losses full retention makes central

These are not constants you retune — they follow from in-place mutation plus keeping every version forever.

1Time-travel degrades by construction

HEAD reads stay O(1), but an as-of read N commits back walks past every newer version — unbounded for a churned key. The MVCC field keeps chains short on purpose (Wu & Pavlo, VLDB 2017: 2.4–3.4× from ordering alone); full retention forfeits that lever.

2Reclamation fights retention

Hazard pointers / EBR / RCU free a node once no in-flight reader needs it. Full time-travel pins that watermark at t₀ forever, so memory grows Θ(total writes) — Böttcher et al.'s “vicious cycle of garbage” that here never resolves.

3Lock-free resize is genuinely hard

Open addressing moves every element on grow; you can't move N items under one CAS. growt's cluster theorem trims it to ~10% but can't remove it. The one design that dissolves resize — split-ordered lists — does it by never moving items: the trie's own idea.

4The string-interning bottleneck

Assigning a code to a never-seen string is a serializing handoff. JVM String.intern degrades ~7,000,000× (to ~650 ms/op) at 1M distinct strings. Column stores sidestep it with delta dictionaries; a single-writer commit just pays it once, locally.

And the trie need not even concede concurrency: Ctrie (Prokopec et al.) is a lock-free concurrent HAMT with single-word CAS and O(1) atomic snapshots — wait-free reads, lock-free writes, and constant-time versioning together.

For TuringDB

Recommendation

Grounded in the code: TuringDB has no dictionary for string property values (only LabelMap for ~128 labels), and its string index today is the per-DataPart prefix trie collected across all parts — the O(parts) fan-out the prior report flagged.

  1. A persistent trie fits the commit model exactly. Each commit's publish becomes one atomic root swap — wait-free reads, free as-of queries, and no version-reclamation problem (old roots are just shared structure old commits hold).
  2. Prefer a radix trie (ART) over a hash trie for strings. No hashing, shallower, smallest memory, and ordered — matching the prefix matching StringIndex already provides. Apply the transferable HAMT tunings: fold each commit, a 64-way default, CHAMP-compact nodes, hash memoization for long keys.
  3. Reserve the lock-free hash for its narrow win: low-cardinality, stable, HEAD-read-only properties where as-of reads are rare. Even there it wants a concurrent dictionary and a reclaimer that full retention can never let finish.
  4. Dictionary-code for memory and ordering, not point reads. Interning dedups bytes and unlocks ordered range scans; it does not speed a trie lookup, and its code-assignment is a write-side cost — cheap in a single-writer commit, expensive in a lock-free table.
  5. Think in two index levels — they compose. A persistent ART as the cross-part global map kills the O(parts) fan-out; per-DataPart indexes are static once built — the ideal case for a succinct trie (SuRF/FST, ~10 bits/key), a range-capable replacement for the per-part Bloom/zone-map prune.

The best way to “improve the HAMT for strings” is to fold + widen + compact it — and then to recognize that for byte-structured keys the persistent radix trie is the better member of the same family. It closes the hash's HEAD-read lead while keeping the time-travel, wait-free, retention-friendly properties that make a persistent structure the right backbone for a versioned store.

Method & caveats

  • A cost model, not a benchmark — operation counts come from executing the workload; latencies from fixed per-op constants. The shapes are the message; retune the constants for your hardware.
  • Node-copy is width-aware (hop + alloc + width·copySlot); folding uses a balls-in-bins expectation under uniform churn (skewed write-sets share more). ART depth is the conservative 256-way bound.
  • Multiversion as-of/reclamation figures are the churned-key worst case; a stable low-cardinality key stays flat — which is why that slice remains the hash's niche.
